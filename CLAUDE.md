# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

pnpm only — npm and yarn are not used here.

```bash
pnpm dev                                  # http://localhost:5124 (pinned; --host to reach it from a phone)
MONGO_URL=mongodb://127.0.0.1:27017 MONGO_DB=nowline_dev PUBLIC_URL=http://localhost:5124 MAIL_TRANSPORT=console pnpm dev:server   # the node process on 3001 (3000 is another project); console prints every email
ulimit -n 64000 && nohup mongod --config /opt/homebrew/etc/mongod.conf &   # see below, and the ulimit is not optional
pnpm test                                 # vitest run, the whole suite
pnpm test client/domain/recurrence.test.ts   # one file
pnpm test -t 'name of the test'           # one test by name
pnpm test:watch
pnpm lint                                 # eslint, on its own
pnpm build                                # lint, then both tsc, then vite build
pnpm build:server                         # tsc into dist-server/; production starts that output
pnpm preview                              # dist/ on http://localhost:5124, the dev origin; stop dev first
```

`pnpm build` is the static gate and runs four things in order, stopping at the first failure: `eslint .`, `tsc --noEmit` for the client, the same for the server, and then `vite build`. The linter is `typescript-eslint` on `strictTypeChecked`, added on 2026-09-10 for the one rule a compiler cannot give — a promise nobody waits for. Five of its rules are argued with in `eslint.config.js`, each with the reason written beside it: two are turned off, two are configured rather than silenced, and one is added — `no-restricted-syntax` against `autoFocus` in JSX, because React applies that attribute before `Sheet` records who had focus, so a sheet that used it handed focus to nothing on close; a sheet asks for the focus with `initialFocus` instead. The largest by far is `no-confusing-void-expression` — 58 hits the day it was turned off, 80 by 2026-09-13 — because `return startClock()` is how this codebase returns a teardown; the one that says most about the design is `require-await` — 24, then 29 — because every repository method here is `async` although `localStorage` is not, which is the seam described below and not an accident. Run the gate before claiming a change compiles. CI runs `pnpm test` and `pnpm build` on every push to `main`, and a failure there stops the deploy before the server is touched; that is a second gate, not a reason to skip the first.

`vite.config.ts` pins `TZ=Europe/Madrid` for the test process, because the developer's own zone (La Paz) has not changed its clocks since 1932 and daylight-saving tests would pass there by proving nothing. Never override it.

The default test environment is `node`. A test that needs a DOM or `localStorage` — rendering React is one case, reading a storage key another — needs `// @vitest-environment jsdom` as its first line.

**The server tests need MongoDB running on 127.0.0.1:27017.** Bringing up the development environment means `pnpm dev` **and** a `mongod`, not just the first — without one, part of the suite fails on a connection error that reads like a bug in the code. Homebrew's `brew services start mongodb-community` does not work: MongoDB's own tap formula declares its service with a name and no `run`, so the generated launch agent has nothing to execute and launchd refuses it with `Bootstrap failed: 5`. `--fork` is no help either — MongoDB rejects it on macOS. `nohup ... &` is what replaces both: it survives the terminal closing, and it does not survive a reboot, which is deliberate — this machine's owner wants to start the database himself rather than find it already running.

**Raise the open-file limit first, every time.** macOS gives a process 256 open files; MongoDB asks for 64000, warns about it on every startup, and then **dies** the moment it runs out mid-operation — which it did here on 2026-09-08, while a test was creating a collection. The tests drop and recreate collections constantly, so exhausting 256 descriptors is the normal case and not an unlucky one. A `mongod` started without the `ulimit` in front of it is a database that will fail during a test run and read like a bug in the code.

Those tests write to `nowline_test_<hash of the test file's path>` and nowhere else — one database per test file, because vitest runs files in parallel and they would otherwise drop each other's collections mid-run. The helper in `server/testing/mongo.ts` refuses any other database or host, because dropping is what it does. Port 27017 is always this machine; 27018 is always a tunnel to production.

**A test that fakes the clock over a collection with a TTL index sets it in the future.** `vi.setSystemTime` moves what the test process writes, not `mongod`'s own clock, and the TTL monitor deletes, every 60 seconds, anything that looks expired against the real one. A login window stamped last week vanished mid-test on 2026-09-15 and reopened a door the test expected shut — intermittently, which is the worst way to find it.

## Architecture

Four layers, dependencies point one way: `ui → state → storage → domain`.

- **`client/domain/`** — pure functions, no React, no DOM: `geometry` (pixels ↔ minutes), `dates` (day keys), `recurrence` (plan + override → what is drawn), `timer` (start/stop/correct), `summary` (totals), `types`.
- **`client/storage/`** — `repository.ts` declares `BlockRepository` and exports the live instance; `localStorageRepository.ts` is the only file in the app allowed to say `localStorage` — the tests say it too, to arrange and assert on what was stored. Every method is `async` although the implementation is synchronous, so a server implementation can replace it without touching a call site. Keys are `nowline.projects.v2`, `nowline.plans.v2`, `nowline.overrides.v2`, plus `nowline.pending.v1` for the ids this device has not uploaded yet, `nowline.sync.v1` (token, the `userId` it belongs to, cursor and `joined`), and `nowline.discarded.<date>` (the copy kept before taking the cloud; never overwritten — `.2`, `.3` are appended), `nowline.<rows>.v2.corrupt` (the raw text of a damaged key, kept before the first overwrite; `.corrupt.2`, `.3` likewise never overwritten), and `nowline.resync.v1` (an ISO stamp, raw: while it exists a full download is owed). The `tt.*.v1` keys this app was born with are migrated once and then **left untouched as a safety net** — do not delete them until every device in use has synced at least once. Every row carries `updatedAt`, written only here; deleting marks `deletedAt` instead of removing the row, and the read methods hide what is marked. A damaged key — an empty string, a non-array, a row without a string `id` — is reported on every read and what can be read is returned; what cannot is never overwritten without a copy: `write` quarantines the raw text under `<key>.corrupt` (then `.corrupt.2`, `.3`…, never overwriting an earlier copy) before the first overwrite, and refuses the overwrite if the copy cannot be written. Corrupt storage must not brick the app, and must not silently delete what was there.
- **`client/state/store.ts`** — one module-level `state` object plus a listener set, exposed with `useSyncExternalStore`. No router, no state library. Mutating functions write through the repository first, then `setState`. It also holds **which of the four things the app shows** — `entry: 'deciding' | 'following-link' | 'signed-out' | 'asking-first-sync' | 'ready'`, with the counts for the first-sync question in `firstSync` and the emailed link being followed in `link` — worked out by `decideEntry()` and **never derived on the fly**: deciding it costs a request, so a component that recomputed it per render would ask the server per render. A link in the URL is looked for **before anything else, the session included**, and read only while `link` is empty, because reading it cleans the address bar; `finishLink()` clears it, reloads the rows and decides again. It also holds `account`, what `GET /api/auth/me` said, asked once by `loadAccount()` when the Account tab mounts and never per render, and `accountFailure`, why there is no answer. The token a signed-in route needs is read here, in `loadAccount`, `resendConfirmation` and `changeAccountEmail`, never by a screen; a `401` on those three does what a rejected round does — sign in again, from the calendar only — and leaves the dead token for the engine to drop. `signOutOfDevice` does not read it: it asks `signOut`, and the engine reads the token behind the one door. And it owns the five moments a round happens: on start, two seconds after any change (debounced), when the tab becomes visible, every five minutes, and thirty seconds after a network failure. `syncNow()` joins a late caller to the round already in flight instead of starting a second one.
- **`server/`** — the Node process: Express on 3001, MongoDB, the `/api/auth/` routes (`register`, `login` by email, `logout`, `me`, `send-confirmation`, `change-email`, `request-reset`, `confirm` and `reset`) plus `POST /api/sync` and `GET /api/health`, and **an error handler as the last `app.use`**. Same split as above — pure logic with no database (`passwords`, `accounts`, `messages`) apart from what talks to Mongo (`db`, `identity`, `attempts`, `links`, `users`, and the routes), plus the one module that talks to the network, `mail`. Which of two copies of a row wins is **not** one of those pure functions: it is the filter of the write in `routes/sync.ts`, because deciding it in JavaScript needs a read and a write with a gap between them, and two overlapping uploads both win in that gap. It compiles with its own `tsconfig.server.json`, because the client one loads the DOM library and Vite's types. Relative imports there need a `.js` extension: the project is ESM and that tsconfig uses `NodeNext`. In production it runs compiled from `dist-server/`, on `127.0.0.1:3001`, behind nginx's `location /api/`, with its configuration in a VPS `.env` that is not in the repository. Email leaves through `server/mail.ts`, the only file that knows a provider exists — `zavuMailer` in production, copied from the request that worked in the owner's own `curl`, and `consoleMailer` in development, which prints every email, link included, on the terminal. The app is built with `createApp(db, { mailer, publicUrl })`, and `readConfig()` refuses to start without `PUBLIC_URL` and `MAIL_TRANSPORT` (and, for `zavu`, `MAIL_API_KEY` and `MAIL_SENDER`), for the same reason `MONGO_DB` has no default. Behind nginx every request reaches Express from `127.0.0.1`, so `app.set('trust proxy', 'loopback')` trusts `X-Forwarded-For` only when the connection itself comes from this machine, where nginx connects from; `true` would let anyone dodge every per-IP limit with a made-up header.
- **`client/ui/`** — React 19 components, plain CSS in `client/styles.css` with BEM-ish class names. No CSS framework, no calendar library. Note this project does **not** use the `gcm-minimalist-design-system` skill; it imitates Google Calendar. Several are not the calendar and share the `.gate` container: `AuthGate`, shown while signed out, which switches between `SignInScreen`, `CreateAccountScreen` and `ForgotPasswordScreen`; `LinkScreen`, shown while an emailed link is followed, whose buttons are the only thing that spends one; `FirstSyncScreen`; and `OtherAccountPrompt`, which every screen that receives a session shows through `useSessionHandoff` — the one way a screen hands a session to the engine. The fourth tab, `account/AccountScreen`, shows what the store holds about the account and hands back three answers — resend, change email (folded out as `ChangeEmailForm`, with the current password through `PasswordField`), sign out (folded out as `SignOutPrompt`, armed after the delay) — and the FAB is not drawn on it. Every refusal the server names becomes a sentence in `failureMessage.ts`, and nowhere else. **None of them decides anything** — the engine does; they show numbers and hand back an answer. A screen that needs a new sync rule is a sign the rule is missing from `client/storage/sync.ts`.

### The data model, which everything else follows from

A repeating block is **one** `BlockPlan` row however many days it appears on. A day that deviates — moved, resized, tracked, deleted — gets a `BlockOverride` keyed by `(planId, date)`. `domain/recurrence.ts` resolves the pair into a `ResolvedOccurrence`, which is the only shape the calendar draws.

Consequence: editing a repeating block in the editor moves every day; dragging one day writes an override and moves only that day.

Tracked time is **never stored as a duration**. An override holds `actualStart`/`actualEnd`, and every total is computed at read time. Do not add a `durationSeconds` field to "cache" it — correction, midnight-crossing sessions and the summary all depend on the raw timestamps.

## Invariants a change can silently break

- **A day is a `'YYYY-MM-DD'` string, never a `Date`.** `new Date('2026-09-07')` is UTC midnight, a different calendar day in most of the world. Build every day key through `client/domain/dates.ts`; a date-only string must not reach `new Date`. `client/ui/sheets/DatePickerSheet.test.ts` fails if the month grid breaks this.
- **The hour scale lives in one constant.** `PIXELS_PER_HOUR = 64` in `domain/geometry.ts`; no code may hardcode 64, 1536 or a pixels-per-minute figure — go through `minuteToPixel` and `DAY_HEIGHT`. The exception is a test asserting a pixel figure, which has to spell the number out or it pins nothing: `TimeBlockView.test.tsx` does, and says where each one comes from. Same for `SNAP_MINUTES` and `MINUTES_PER_DAY`. Pinch-to-zoom is a planned feature that turns that constant into a variable.
- **Positions and heights are wall-clock, not elapsed.** Use `minutesSinceMidnight` and `wallClockMinutesBetween` from `domain/dates.ts`, so the two daylight-saving days line up. Elapsed-time arithmetic (`(end - start) / 60000`) is wrong for anything drawn.
- **`overflow-anchor: none` on `.calendar__scroll` must stay,** and so must the manual `scrollTop` compensation in `useInfiniteDays.ts`. The strip keeps seven days mounted and compensates when it prepends one; Chromium and Firefox do the same compensation themselves, so with both the strip jumps a whole day. Browsers without scroll anchoring need the manual half. No unit test catches this.
- **One timer at a time.** `startTimerFor`/`stopRunningTimer` are serialised on a promise queue in `state/store.ts`, and a start re-reads overrides from the repository before deciding. The internal `*Unlocked` variants must not take the lock — start calls stop. Two tabs can still race; closing that needs an atomic compare-and-set the repository cannot offer.
- **Block text colour is computed, not chosen.** `ui/textColor.ts` picks black or white per project colour for contrast, and dims a tracked block by blending its **background** toward the page colour. Never use CSS `opacity` for that — it fades the text too and cancels the contrast out.
- **A block may cross midnight, and is drawn once.** One rectangle that overflows its day section, which sets no `overflow`; `.block` carries `z-index: 1` so the next day's grid does not paint over the overhang. What still holds: a block starts inside the day it belongs to, and lasts at most 24 hours — the second is what bounds the overflow to one day. `occurrencesForDay` returns what belongs to a date, never what passes through it.
- Deleting reads the plan's **stored** recurrence, never the unsaved dropdown.
- Errors the app recovers from go through `reportError`/`reportWarning` in `client/reportError.ts` rather than being swallowed.

### The sync invariants, which are the easiest to break and the hardest to notice

Every one of these was a real defect first, found by a review rather than by a tool. They are written here because a wrong change to any of them loses a row quietly.

- **One door, and the bodies inside it call each other directly.** `syncOnce`, `inspectFirstSync`, `settleFirstSync`, `adoptSession` and `signOut` all read and write the same things — this device's queue, its cursor, and whose rows it holds — so they go through one serialised queue (`oneAtATime` in `client/storage/sync.ts`). Their unwrapped bodies (`runSyncOnce` and the others) call each other **without** taking the lock, because a resolution runs a round inside itself and asking for a lock it already holds deadlocks. If the suite ever hangs instead of failing, look here first.
- **`touch` is the only place that *invents* an `updatedAt`,** for a row this device changed, and it compares against that row's own previous stamp. Three other places write the field and **none of them may go through `touch`**: `ensureMigrated` invents one for legacy rows, and `applyFromServer` and `replaceAllFromServer` keep the stamp that arrived. Restamping a download with this device's clock is the infinite ping-pong between two devices.
- **`joined` gates everything, and within one account on one device it only ever goes from false to true.** Until it is true every round returns `needs-first-sync`, which is what stops a device merging before its owner has chosen. Signing in again after an expired token is not joining again, and the question it would re-ask has an answer that replaces every row written since. The one way back to false is a change of owner in `adoptSession`, and never the flag alone. For rows known to be another account's, `resetDevice` empties rows, queue and marker first, after a copy of anything no cloud has, and only then is `joined: false` written with the new token. The one case that keeps the rows is a device from before accounts (`userId: null`) whose holder says they are theirs: `joined: false` is written over them on purpose, so the first-sync question — not a round — decides what happens to them, and the cursor is reset with it. A false flag over another account's rows is the blind merge the flag exists to prevent.
- **A device holds one account's rows.** `nowline.sync.v1` records the `userId` beside the token, and every writer of that state carries it through. `adoptSession` in `sync.ts` is the only way a token from outside the engine reaches it: the same account changes the token and nothing else; another account's rows leave first; a device from before accounts (`userId: null`) that holds rows asks whoever holds it. A screen that writes the token itself is how one person's queue gets uploaded into someone else's cloud. Emptying writes `[]` and never removes a key, because `ensureMigrated` refills a missing v2 key from `tt.*.v1`.
- **The cursor is the newest stamp actually handed over, never the wall clock,** and the filter is `$gte`. A clock cursor can run ahead of a row another request is still writing, and `$gt` would skip it for good. `$gte` re-sends the row sitting on the boundary: one row per round, and nothing lost.
- **A plan tombstone drops that plan's overrides, on whichever device sees it.** An override carries no tombstone of its own, so `deletePlan` and `applyFromServer` share one private method for the cascade — and it runs **after** the override merge, because a catch-up reply carries the override from before the deletion and the tombstone from after it. Skip it on the receiving side and a running override with no plan to stop it stays behind, invisible and counted.
- **A full download is owed from the moment damaged content is overwritten, and only from then.** `write` raises `nowline.resync.v1` when it quarantines and overwrites; `read` never does, because a damaged key nothing writes to would ask for a full download on every round for ever. `runSyncOnce` sends `cursor: null` while the marker stands and clears it **only if it is still the value it read at the start of the round** — a marker raised by an `applyFromServer` inside the round is newer, survives, and the next round pays it. Clearing by the wall clock is how that reset was lost the first time. `take-the-cloud` is a full download by construction, so it reads the marker **after** the replacement and clears that value: the marker the replacement itself raised is already paid, and reading before it — as `runSyncOnce` rightly does — would leave that one standing for a second download nobody needs.
- **Signing out uploads first, asks, revokes, and only then empties.** `signOut` in `client/storage/sync.ts` runs one round (offline or refused: nothing changes; unauthorized: the token is already dead, so the revoke is skipped; not joined: no round, every row is at risk), counts what no cloud has and answers `at-risk` unless told to discard, asks the server to forget the session, and then `resetDevice` with a copy of anything at risk. The revoke comes before the reset on purpose: if the reset throws, the device holds a dead token and its next round shows "Sign in", which is the safe direction. Signing out reaches the server, like an upload does.

### The account invariants

- **An email is stored normalized** — trimmed and lowercased by `normalizeEmail` in `server/accounts.ts` — and every route normalizes before it queries or stores. Mongo's unique index is case-sensitive, so without this `Ana@x` and `ana@x` would be two accounts.
- **The unique index on `users.email` is partial** (`email: { $type: 'string' }`). A released account holds `email: null`, and a plain unique index would allow only one of them. `connect()` also drops the old `username_1` index, in code and not as a manual step: a unique index treats a missing field as `null`, so with it the second registration would collide with the first and be told its address is taken.
- **A link URL comes only from `PUBLIC_URL`**, never from the request's `Host` header. Someone requests a reset for the victim with `Host: evil.example`, and the victim's email would otherwise carry a link to that host.
- **A link is consumed in one operation** — `consumeLink` is a `findOneAndDelete` with the purpose and `expiresAt > now` in its filter — so two presses of one link cannot both succeed, and a link that expired a minute ago does not get through while Mongo's TTL monitor (every 60 s) has not yet removed it. Issuing a link deletes the earlier ones of the same user and purpose: the latest email is the one that works. On the client, a link is consumed by a button, never by loading the page. It arrives in the URL fragment (`#confirm=<token>`, `#reset=<token>`), which the browser never sends and nginx therefore never logs, and `takeEmailLink` in `client/state/emailLink.ts` removes it from the address bar the moment it reads it, malformed or not, so the secret stays out of the history and of any bookmark.
- **An unconfirmed account older than 24 hours does not keep its address** from someone who wants it. `releaseStaleHolder` in `server/users.ts` sets its `email` to `null`, measured by `createdAt` — which nobody can refresh — and never by a link's age. It runs before `register` inserts and before a `change-email` link sets the address. The released account keeps its rows, its password and its sessions: no row ever reaches another person.
- **A password reset goes only to a confirmed address**, because it is the link that takes an account over. `request-reset` answers `200 {}` for every address and does its lookup and its sending after the reply, so neither the body nor the time says whether an account exists. A successful reset revokes every session of the account.
- **A wrong current password on a signed-in route answers `403`, never `401`.** The client's `apiClient.post` reads any `401` as `unauthorized` and signs the device out, so a typo on "Change email" would otherwise end the session. `change-email` asks for that password because an unlocked phone in someone else's hands must not move the account's recovery to their inbox, and counts the attempt before comparing it.
- **The notice of an email change goes to the old address only if that address was confirmed**, after the reply. A notice never goes to a typo or to a stranger.
